---
title: 权限
description: 配置权限守卫的风险策略与按应用覆盖。
---

权限守卫对每次工具调用决定：直接执行、执行并提示、挂起询问，还是拒绝。这个决定是工具声明风险与策略的纯函数。

## 风险 → 动作

| 风险 | 默认动作 |
|------|----------|
| `low` | `auto` — 静默执行 |
| `medium` | `notify` — 执行并提示 |
| `high` | `confirm` — 挂起直到你决定 |
| `critical` | `deny` — 拒绝 |

## 默认策略

```ts
defaultPolicy: {
  low: "auto",
  medium: "notify",
  high: "confirm",
  critical: "deny",
}
```

这是守护进程实际运行的策略，映射定义在 `@jarvis/permission-guard` 中并作用于每次工具调用。

**它目前还不支持用户配置。** 守卫以默认值构造，`config.json` 中也没有权限段落——本文件历史版本描述过一个 `permissions.rules` 数组，那个数组并不存在，写进去也不会生效。

## 按应用覆盖

守卫的配置结构支持按应用覆盖：

```ts
appPermissions: {
  "filesystem": { write: true,  execute: false },
  "untrusted-mcp": { write: false, execute: false },
}
```

各标志的映射：

| 风险 | `write: true` | `write: false` |
|------|---------------|----------------|
| `medium` | `notify` | `confirm` |
| `high` | `confirm` | `deny` |

| 风险 | `execute: true` | `execute: false` |
|------|-----------------|------------------|
| `critical` | `confirm` | `deny` |

`low` 始终是 `auto`。

覆盖在存在时会被评估，但守护进程中目前没有代码从磁盘读取它们，因此只对以覆盖配置构造守卫的调用方生效。

## 语音模式

语音执行不论风险都更严格：只读动作自动放行，其余都需要确认。口头发起比手动输入更容易被误触发。

## 审批请求

动作为 `confirm` 时，守卫不会把决定留在内存里：

1. 持久化 `approval_request`，包含动作摘要、风险、范围与过期时间
2. 挂起运行
3. 界面展示请求——批准、拒绝或记住
4. 决定后恢复或终止运行

端点：

```text
GET  /api/approvals
GET  /api/approvals/:id
POST /api/approvals/:id/approve
POST /api/approvals/:id/deny
POST /api/approvals/:id/remember
POST /api/approvals/batch/approve
POST /api/approvals/batch/deny
POST /api/approvals/expire-stale
```

“请求已过期”是真实状态：无人值守队列会堆积没人应答的请求，`expire-stale` 会把它们关闭，而不是让运行永久挂起。

## 权限记忆

“记住”会把决定记录在动作摘要上——是具体动作，而不是工具名。同一动作不再询问；不同路径、命令或参数集合会产生不同摘要，仍会询问。

## 审计

每次决定都写入 `audit_log`，可按条件查询：

```text
GET /api/audit?actor=jarvis&action=tool.execute&riskLevel=high&since=2026-10-01T00:00:00Z&limit=50
```

一条记录包含 `actor`、`action`、`resource`、`riskLevel`、`permissionDecision`、`confirmedByUser`、`result`、`metadata` 与 `createdAt`。
