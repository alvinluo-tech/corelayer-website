---
title: 多執行階段演進方向
description: 長期架構目標，以及今天真實的狀態。
---

CoreLayer 目前是單一 Node.js 守護行程，在行程內承載六個已註冊執行階段。長期目標是 Rust/Tauri 核心透過顯式的權限、稽核、更新與執行階段協定來監管多個受管執行階段。

本頁刻意區分「已存在」與「計畫中」，因為此前版本的文件把二者混為一談。

## 今天

```text
Tauri 桌面外殼（Rust）
  └─ Node.js 守護行程（Hono）
       ├─ agent       （已註冊）
       ├─ tool        （已註冊）
       ├─ coding      （已註冊）
       ├─ memory      （已註冊）
       ├─ voice       （已註冊）
       └─ scheduler   （已註冊）

       computer-control   （模組已實作，未註冊）
```

執行階段宿主已提供註冊、生命週期與狀態，`GET /api/runtime/components` 會上報各註冊執行階段的健康狀況。這屬於**行程內監管**，不是行程隔離。

## 目標

```text
Tauri/Rust 核心
  ├─ 執行階段監管器（啟動、重啟、資源限制）
  ├─ 基於 IPC 的 Runtime Protocol
  ├─ agent / tool / coding / memory / voice / scheduler 作為受管行程
  └─ Computer control（Rust，真正的作業系統能力）
```

每個受管執行階段應當：

- 獨立行程執行，可單獨重啟
- 只透過 `@jarvis/runtime-protocol` 通訊
- 擁有自己的資源上限
- 能力顯式授予，絕不隱式取得

## 遷移路徑

1. **目前** — 單守護行程，模組邊界由匯入測試與各執行階段 `public-api.ts` 強制
2. **下一步** — 抽出故障域已經分化的執行階段（coding、voice）
3. **之後** — 把監管器從 Node 守護行程移入 Rust 核心
4. **最終** — computer control 建立在真實的原生能力之上，而非空殼

每一步都保持 HTTP 契約穩定，因此前端無需改動。

## 為什麼不做整體 Rust 重寫

守護行程的職責不是 CPU 密集：它是編排、策略與持久化。整體重寫為 Rust 收益有限，卻會犧牲治理模型仍在演進時最需要的迭代速度。真正適合 Rust 的是監管器與原生能力——這也正是目標架構安排的位置。

## 什麼情況下本頁會過時

如果 computer control 被註冊且具備真實能力，或某個執行階段開始以獨立行程執行、擁有獨立生命週期，請在同一次變更中更新本頁。把目標當成現狀來描述，正是本頁要防止的失敗模式。
