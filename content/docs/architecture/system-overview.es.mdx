CoreLayer es un **Agent OS** de escritorio local-first. Un shell de Tauri aloja la UI y supervisa un daemon de Node.js; el daemon posee todos los runtimes, todas las llamadas a herramientas y todo el estado persistido.

Esta pagina describe lo que realmente contiene el sistema en ejecucion. Para la direccion a largo plazo, consulta [Direccion Multi-Runtime](/docs/architecture/multi-runtime-direction).

## Topologia

```text
┌──────────────────────────────────────────────────────────────┐
│ Shell de escritorio Tauri (Rust)                             │
│   ├─ UI Webview (React 19 + Vite + Tailwind)                 │
│   ├─ Supervisor del daemon: arranque / salud / reinicio      │
│   └─ Proxy HTTP → daemon local                               │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP (solo loopback, puerto 3001)
┌───────────────────────────┴──────────────────────────────────┐
│ Daemon Node.js (TypeScript + Hono)                           │
│                                                              │
│  Host de runtimes (registro · ciclo de vida · estado)        │
│   ├─ agent        — bucle de conversacion y tool calling      │
│   ├─ tool         — registro, enrutado, herramientas nativas  │
│   ├─ coding       — adaptadores de ejecutor, worktrees, gates │
│   ├─ memory       — memoria de largo plazo y snapshots        │
│   ├─ voice        — wake word, ASR, TTS, barge-in             │
│   └─ scheduler    — trabajo autonomo por cron                 │
│                                                              │
│  Plano de workflow                                           │
│   ├─ run dispatcher / queue / slot manager                   │
│   ├─ delegation (narrowing monotono)                         │
│   ├─ ejecutor de DAG de task graph                           │
│   └─ adjudication (juez adversarial)                         │
│                                                              │
│  Transversal                                                 │
│   ├─ Permission guard + aprobaciones (HITL)                  │
│   ├─ Audit log + event log                                   │
│   └─ Persistencia (SQLite por defecto; Supabase/PostgreSQL)   │
└──────────────────────────────────────────────────────────────┘
```

## Capas

### Frontend (React)

Renderiza conversaciones, workspaces, ejecuciones, aprobaciones y ajustes. Habla con el daemon solo a traves del puente de Tauri; nunca abre una base de datos ni una conexion a un proveedor por si mismo.

### Puente de Tauri (Rust)

Arranca y supervisa el sidecar del daemon, reenvia llamadas HTTP y provee capacidades nativas (rutas, ventana, bandeja). Todos los comandos IPC estan registrados explicitamente.

### Daemon (Node.js)

El unico componente con autoridad. Mantiene el registro de runtimes, ensambla el contexto, llama a modelos por el Model Gateway, ejecuta herramientas detras del Permission Guard y persiste todo a traves de la capa de repositorios.

### Paquetes compartidos

El daemon compone ocho paquetes del workspace en lugar de duplicar su logica:

| Paquete | Rol |
|---------|-----|
| `@jarvis/types` | Tipos TypeScript compartidos |
| `@jarvis/model-gateway` | Resolucion de proveedor y enrutado de modelos |
| `@jarvis/mcp-client` | Conexiones MCP (stdio, HTTP, SSE) |
| `@jarvis/tool-registry` | Catalogo y resolucion de herramientas |
| `@jarvis/permission-guard` | Clasificacion de riesgo, politica, auditoria |
| `@jarvis/runtime-core` | Primitivas de ciclo de vida de runtime |
| `@jarvis/runtime-protocol` | Definiciones del contrato de runtime |
| `@jarvis/execution-environment` | Abstraccion de ejecucion (basada en worktree) |

## Que esta registrado

El registro de runtimes vive en `daemon/src/runtimes/index.ts`. Seis runtimes estan registrados en el host y reportan estado por `GET /api/runtime/components`:

`agent`, `tool`, `coding`, `memory`, `voice`, `scheduler`.

**Computer control no esta registrado.** Sus capas de riesgo, permisos y auditoria existen y sus herramientas estan definidas, pero la ruta de ejecucion aun no toca el sistema operativo y no hay capacidad del lado de Rust que lo respalde. Registrarlo anunciaria un runtime que no hace nada, asi que se mantiene fuera hasta que exista una implementacion real. Cualquier documentacion (incluidas versiones anteriores de estas paginas) que lo liste como runtime activo es incorrecta.

## Comunicacion

```text
Entrada del usuario
  → frontend React
  → IPC de Tauri
  → supervisor Rust del daemon (proxy HTTP)
  → ruta Hono (/api/conversations/:id/messages/stream, /api/chat/stream, …)
  → runtime agent: ensamblado de contexto → modelo → tool calls → politica de completion
  → respuesta SSE / JSON por el mismo camino
```

El trabajo de larga duracion no bloquea un turno de chat: el dispatcher persiste un `agent_run`, la cola reserva un slot y los eventos se escriben en el event log mientras avanza. Los clientes los leen con `GET /api/events` y `GET /api/runs/:id/events`.
