---
title: Limites de Runtime
description: Que cruza cada limite y que puede hacer cada capa.
---

CoreLayer separa la UI, el shell de escritorio, el daemon y los procesos externos para que un fallo en una capa no escale silenciosamente hacia otra.

## Modelo de limites

```text
UI Webview (React)
  ║ IPC de Tauri — solo comandos tipados y registrados
  ╚═► Shell de Tauri (Rust)
      ║ HTTP — solo loopback
      ╚═► Daemon Node.js (Hono)
          ║ llamadas en proceso (modulos public-api)
          ╠═► paquetes compartidos
          ║ subproceso / red
          ╠═► proceso ejecutor ACP (Claude Code, Codex, OpenCode)
          ╠═► servidores MCP (subproceso stdio o HTTP/SSE)
          ╚═► base de datos (archivo SQLite, Supabase, PostgreSQL)
```

## Reglas entre limites

| Limite | Regla |
|--------|-------|
| UI → Tauri | Solo comandos registrados; sin acceso directo a sistema de archivos ni red |
| Tauri → daemon | HTTP en loopback; el puerto se elige al arrancar y se reporta en `/api/runtime/status` |
| Daemon → paquetes | Importar por el `public-api.ts` de cada runtime, nunca a modulos internos |
| Daemon → ejecutor | Proceso hijo en un worktree git, con modelo/ejecutor fijos y un sobre de limites estrechado |
| Daemon → servidor MCP | Subproceso stdio o HTTP/SSE remoto; cada herramienta reportada se registra con su riesgo |
| Daemon → base de datos | Solo por la capa de repositorios; ninguna ruta consulta la base directamente |

Uno de ellos se aplica de forma mecanica: una prueba de limites de importacion rompe el build si una ruta HTTP entra en los internals de un runtime en lugar de su `public-api.ts`.

## UI ↔ Tauri

- Comandos tipados en ambos lados (TypeScript ↔ structs de Rust)
- Payloads JSON
- Llamadas asincronas; la UI nunca se bloquea esperando el arranque del daemon

## Tauri ↔ daemon

- HTTP, solo loopback. `/api/runtime/shutdown` ademas rechaza peers que no sean loopback.
- SSE para chat en streaming y progreso de ejecuciones
- El shell es dueno del ciclo de vida: arranque, health check, reinicio tras caida, terminacion al salir

## Daemon ↔ ejecutores

El trabajo de codigo no se ejecuta dentro del daemon. El runtime coding lanza un agente externo mediante un adaptador (ver [Adaptadores de Ejecutores](/docs/guides/coding-executors)) dentro de un worktree git aislado, y solo lee eventos estructurados, artefactos y un diff. Lo que el hijo puede hacer queda fijado en el despacho por los [limites de delegacion](/docs/architecture/executor-governance#delegation-bounds) y el hijo no puede ampliarlos.

## Por que importa

- **Contencion** — un ejecutor descontrolado solo puede danar su propio worktree
- **Atribucion** — cada cambio de estado tiene run id, actor y entrada de auditoria
- **Reemplazabilidad** — un proveedor, ejecutor o backend de almacenamiento se sustituye sin tocar los demas
- **Testabilidad** — los limites se aplican con pruebas, no solo por convencion
