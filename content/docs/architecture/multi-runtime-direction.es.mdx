---
title: Direccion Multi-Runtime
description: El objetivo de arquitectura a largo plazo y lo que es cierto hoy.
---

CoreLayer corre como un unico daemon de Node.js que aloja seis runtimes registrados en proceso. El objetivo a largo plazo es un nucleo Rust/Tauri que supervise multiples runtimes gestionados mediante protocolos explicitos de permisos, auditoria, actualizacion y runtime.

Esta pagina separa lo que existe de lo que esta planificado, porque versiones anteriores de la documentacion mezclaban ambos.

## Hoy

```text
Shell de escritorio Tauri (Rust)
  └─ Daemon Node.js (Hono)
       ├─ agent       (registrado)
       ├─ tool        (registrado)
       ├─ coding      (registrado)
       ├─ memory      (registrado)
       ├─ voice       (registrado)
       └─ scheduler   (registrado)

       computer-control   (modulos implementados, NO registrado)
```

El host de runtimes ya provee registro, ciclo de vida y estado, y `GET /api/runtime/components` reporta la salud de cada runtime registrado. Eso es supervision en proceso, no aislamiento de procesos.

## Objetivo

```text
Nucleo Tauri/Rust
  ├─ Supervisor de runtimes (arranque, reinicio, limites de recursos)
  ├─ Runtime Protocol por IPC
  ├─ agent / tool / coding / memory / voice / scheduler como procesos gestionados
  └─ Computer control (Rust, capacidad nativa real)
```

Cada runtime gestionado deberia:

- ejecutarse en su propio proceso, reiniciable de forma independiente
- comunicarse solo por `@jarvis/runtime-protocol`
- tener su propio sobre de recursos
- recibir capacidades de forma explicita, nunca implicita

## Ruta de migracion

1. **Actual** — daemon unico con limites de modulo aplicados por pruebas de importacion y fachadas `public-api.ts` por runtime
2. **Siguiente** — extraer los runtimes cuyos dominios de fallo ya divergen (coding, voice)
3. **Despues** — mover el supervisor del daemon Node al nucleo Rust
4. **Final** — computer control detras de una capacidad nativa real, no un stub

Cada paso mantiene estable el contrato HTTP, asi que el frontend no cambia.

## Por que no reescribir todo en Rust

La autoridad del daemon no esta limitada por CPU: es orquestacion, politica y persistencia. Reescribirlo en Rust daria poco rendimiento extra y costaria la velocidad de iteracion que importa mientras el modelo de gobernanza sigue evolucionando. Donde Rust aporta es el supervisor y las capacidades nativas, que es donde el objetivo lo coloca.

## Que haria incorrecta esta pagina

Si computer control se registra y esta respaldado por una capacidad real, o si un runtime pasa a correr como proceso separado con su propio ciclo de vida, actualiza esta pagina en el mismo cambio. Describir el objetivo como estado actual es el modo de fallo que esta pagina existe para evitar.
