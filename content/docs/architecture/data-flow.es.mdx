Esta pagina traza los tres flujos que importan: un turno de chat, una llamada a herramienta dentro de ese turno y una ejecucion despachada que sobrevive al turno.

## Turno de chat

```text
1. El usuario envia un mensaje desde el panel de chat
2. Frontend → IPC de Tauri → HTTP del daemon
     POST /api/conversations/:id/messages/stream   (o POST /api/chat/stream)
3. El runtime agent ensambla el contexto:
     - historial de conversacion (por conversacion, con ramas)
     - memoria de largo plazo recuperada del runtime memory
     - el conjunto de herramientas core, mas herramientas on-demand elegidas por el router
4. El Model Gateway resuelve proveedor/modelo activo y abre una llamada en streaming
     (Vercel AI SDK v6; el control de pasos ocurre en prepareStep)
5. Cada paso puede:
     - emitir texto → streameado a la UI
     - pedir una tool call → flujo de abajo
6. Los loop breakers y el presupuesto de pasos deciden si el turno continua
7. La politica de completion y los quality gates deciden si el resultado es aceptable
8. El mensaje final se persiste y el stream SSE se cierra
```

## Llamada a herramienta

```text
El modelo pide una herramienta
  → el Tool Registry la resuelve (native / MCP / skill)
  → el Permission Guard lee el riesgo declarado (no inferido)
  → decision de politica:
      auto    → ejecutar
      notify  → ejecutar y notificar
      confirm → crear solicitud de aprobacion, suspender la ejecucion, reanudar al decidir
      deny    → bloquear y registrar
  → ejecutar
  → escribir entrada de auditoria (actor, accion, riesgo, decision, resultado)
  → devolver el resultado al modelo
```

Las aprobaciones se persisten, no viven en memoria: una solicitud pendiente sobrevive a un reinicio del daemon y el servicio de reanudacion la continua cuando el usuario decide.

## Ejecucion despachada

```text
Objetivo del usuario / tarea delegada
  → el run dispatcher valida los limites (delegar solo puede estrechar)
  → una entrada de cola toma un slot (la concurrencia esta acotada por clase de recurso)
  → el runtime coding crea un worktree git
  → el adaptador de ejecutor lanza el agente hijo (ACP)
  → sonda de capacidades: ready / needs_auth / unreachable
  → el hijo emite eventos en streaming → event mapper → event log
  → diff y artefactos se guardan en el registro de la ejecucion
  → quality gates / juez adversarial (si estan activos)
  → politica de completion: pasa → rama entregable; falla → fallo con motivo
```

Cada transicion escribe un evento de `agent_run`, por eso `GET /api/runs/:id/events` puede reconstruir una ejecucion a posteriori y por eso una ejecucion se puede cancelar o reintentar por id.

## Conexion MCP

```text
1. El daemon carga las definiciones desde mcp-servers.json
2. Lanza el subproceso (stdio) o conecta por HTTP/SSE
3. Handshake initialize de MCP
4. Lee la lista de herramientas y registra cada una con su politica de riesgo
5. Las herramientas quedan disponibles para el router y el modelo
6. Al desconectarse se marca disconnected y se puede reiniciar
```

## Escrituras de almacenamiento

```text
Ruta o runtime → repositorio (SQLite / Supabase / PostgreSQL)
  → validacion de esquema
  → escritura
  → (si es evento) tambien se agrega al event log
```

El modo de almacenamiento se lee al arrancar desde `storage.json` (`local`, `cloud`, `postgres`). Ver [Almacenamiento](/docs/configuration/storage).

## Turno de voz

```text
Wake word → se abre el microfono → ASR streamea transcripciones parciales y finales
  → la transcripcion final entra al pipeline de chat igual que texto escrito
  → la respuesta se streamea; TTS lee oraciones completas
  → barge-in: hablar durante la reproduccion interrumpe el audio y vuelve al ASR
```
