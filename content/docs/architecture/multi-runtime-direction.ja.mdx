---
title: マルチランタイムの方向性
description: 長期的なアーキテクチャ目標と、今日の実際の状態。
---

CoreLayer は現在、6 つの登録済みランタイムをプロセス内で抱える単一の Node.js デーモンとして動作します。長期的な目標は、明確な権限・監査・更新・ランタイムプロトコルを通じて複数の管理ランタイムを監督する Rust/Tauri コアです。

本ページは「既に存在するもの」と「計画中のもの」を意図的に分けます。以前のバージョンの文書は両者を混同していました。

## 今日

```text
Tauri デスクトップシェル（Rust）
  └─ Node.js デーモン（Hono）
       ├─ agent       （登録済み）
       ├─ tool        （登録済み）
       ├─ coding      （登録済み）
       ├─ memory      （登録済み）
       ├─ voice       （登録済み）
       └─ scheduler   （登録済み）

       computer-control   （モジュールは実装済み、未登録）
```

ランタイムホストは登録・ライフサイクル・ステータスを既に提供し、`GET /api/runtime/components` が各登録ランタイムの健全性を報告します。これは**プロセス内監督**であり、プロセス分離ではありません。

## 目標

```text
Tauri/Rust コア
  ├─ ランタイム監督者（起動、再起動、リソース制限）
  ├─ IPC 上の Runtime Protocol
  ├─ agent / tool / coding / memory / voice / scheduler を管理プロセスとして
  └─ Computer control（Rust、本物の OS 機能）
```

各管理ランタイムは：

- 独立プロセスで動き、単独で再起動できる
- `@jarvis/runtime-protocol` だけで通信する
- 独自のリソース上限を持つ
- 能力は明示的に付与され、暗黙に得ることはない

## 移行パス

1. **現在** — 単一デーモン。モジュール境界はインポートテストと各ランタイムの `public-api.ts` で強制
2. **次** — 障害領域が既に分かれたランタイム（coding、voice）を抽出
3. **その後** — 監督者を Node デーモンから Rust コアへ移す
4. **最終** — computer control をスタブではなく本物のネイティブ機能の背後に置く

各段階で HTTP 契約は安定したままなので、フロントエンドは変わりません。

## なぜ Rust で全面書き直さないか

デーモンの権限は CPU バウンドではありません。オーケストレーション、ポリシー、永続化です。Rust で書き直してもスループットの利得は小さく、ガバナンスモデルがまだ進化している間に必要な反復速度を失います。Rust が価値を発揮するのは監督者とネイティブ機能であり、目標アーキテクチャもそこに置いています。

## 本ページが誤りになる条件

computer control が登録され本物の機能に裏打ちされた場合、またはあるランタイムが独立プロセスとして独自ライフサイクルで動き始めた場合は、同じ変更で本ページを更新してください。目標を現状として記述することが、本ページが防ごうとしている失敗モードです。
