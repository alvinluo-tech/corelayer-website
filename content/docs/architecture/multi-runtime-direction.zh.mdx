title: 多运行时演进方向
description: 长期架构目标，以及今天真实的状态。
---

CoreLayer 目前是单个 Node.js 守护进程，在进程内承载六个已注册运行时。长期目标是 Rust/Tauri 核心通过显式的权限、审计、更新与运行时协议来监管多个受管运行时。

本页刻意区分“已存在”与“计划中”，因为此前版本的文档把二者混为一谈。

## 今天

```text
Tauri 桌面外壳（Rust）
  └─ Node.js 守护进程（Hono）
       ├─ agent       （已注册）
       ├─ tool        （已注册）
       ├─ coding      （已注册）
       ├─ memory      （已注册）
       ├─ voice       （已注册）
       └─ scheduler   （已注册）

       computer-control   （模块已实现，未注册）
```

运行时宿主已提供注册、生命周期与状态，`GET /api/runtime/components` 会上报各注册运行时的健康状况。这属于**进程内监管**，不是进程隔离。

## 目标

```text
Tauri/Rust 核心
  ├─ 运行时监管器（启动、重启、资源限制）
  ├─ 基于 IPC 的 Runtime Protocol
  ├─ agent / tool / coding / memory / voice / scheduler 作为受管进程
  └─ Computer control（Rust，真正的操作系统能力）
```

每个受管运行时应当：

- 独立进程运行，可单独重启
- 只通过 `@jarvis/runtime-protocol` 通信
- 拥有自己的资源上限
- 能力显式授予，绝不隐式获得

## 迁移路径

1. **当前** — 单守护进程，模块边界由导入测试与各运行时 `public-api.ts` 强制
2. **下一步** — 抽出故障域已经分化的运行时（coding、voice）
3. **之后** — 把监管器从 Node 守护进程移入 Rust 核心
4. **最终** — computer control 建立在真实的原生能力之上，而非空壳

每一步都保持 HTTP 契约稳定，因此前端无需改动。

## 为什么不做整体 Rust 重写

守护进程的职责不是 CPU 密集：它是编排、策略与持久化。整体重写为 Rust 收益有限，却会牺牲治理模型仍在演进时最需要的迭代速度。真正适合 Rust 的是监管器与原生能力——这也正是目标架构安排的位置。

## 什么情况下本页会过时

如果 computer control 被注册且具备真实能力，或某个运行时开始以独立进程运行、拥有独立生命周期，请在同一次变更中更新本页。把目标当成现状来描述，正是本页要防止的失败模式。
