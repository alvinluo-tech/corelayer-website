---
title: Permission Guard
description: Control de ejecucion por riesgo, con aprobaciones persistidas y auditoria completa.
---

El Permission Guard se interpone entre el modelo y cada efecto secundario. Clasifica una llamada por el riesgo declarado en la herramienta, aplica la politica y, cuando la respuesta es "preguntar", suspende el trabajo en lugar de adivinar.

## Modelo de riesgo

Cuatro niveles, cada uno asociado a una accion:

| Riesgo | Accion por defecto | Herramientas tipicas |
|--------|--------------------|----------------------|
| `low` | `auto` | Lectura, consulta, descubrimiento, esqueleto de codigo |
| `medium` | `notify` | Crear o actualizar tarea, agregar articulo, guardar revision |
| `high` | `confirm` | Borrar, despachar agente, ejecutar task graph |
| `critical` | `deny` | Bloqueado salvo concesion explicita |

Las anulaciones por app endurecen o relajan un nivel (se evaluan cuando se construye el guard con ellas; el daemon usa los valores por defecto):

```ts
appPermissions: {
  "some-app": { write: false, execute: false }
}
// medium → confirm (write: false)
// high   → deny    (write: false)
// critical → deny  (execute: false)
```

La ejecucion por voz es mas estricta: solo las acciones de lectura se aprueban automaticamente, todo lo demas requiere confirmacion.

## Por que el riesgo se declara

La inferencia desde nombres y argumentos falla en una direccion predecible. `dispatch_agent` y `run_task_graph` no contienen palabras de riesgo pero lanzan ejecuciones que escriben archivos y ejecutan comandos; la inferencia por nombre las clasifico `low`, que la politica por defecto aprueba. Por eso el registro exige un nivel de riesgo explicito para cada herramienta nativa.

## Flujo de aprobacion

```text
Tool call o solicitud de permiso de un ejecutor
  → se lee el riesgo de la definicion de la herramienta
  → politica: auto / notify / confirm / deny
  → confirm: se persiste una solicitud de aprobacion
      - digest de accion (que se ejecutara exactamente)
      - riesgo, alcance, expiracion
  → se suspende la ejecucion
  → decision en la UI: aprobar / denegar / recordar
  → el servicio de reanudacion continua o falla la ejecucion
  → se escribe auditoria en cualquier caso
```

Como las aprobaciones se persisten, una decision pendiente no se pierde al reiniciar el daemon. `POST /api/approvals/expire-stale` cierra solicitudes que nadie respondio, y existen endpoints por lote para colas acumuladas sin atencion.

## Memorias de permiso

"Recordar" registra una decision contra el digest de la accion, asi la accion identica no se vuelve a preguntar. Esta acotado: una ruta, comando o conjunto de parametros distinto es otro digest y se vuelve a preguntar.

## Auditoria

Cada decision se escribe con actor, accion, riesgo, decision y resultado. Las entradas se consultan con `GET /api/audit` y los filtros `actor`, `action`, `riskLevel`, `since`, `limit` y `offset`.

El audit log es distinto del event log: la auditoria responde "que se permitio o denego", el event log responde "que ocurrio durante esta ejecucion" (`GET /api/events`).

## Inspeccionar el estado

- `GET /api/approvals` — pendientes y recientes
- `GET /api/approvals/:id` — una solicitud
- `POST /api/approvals/:id/approve` / `deny` / `remember`
- `GET /api/audit?riskLevel=high` — decisiones de alto riesgo
