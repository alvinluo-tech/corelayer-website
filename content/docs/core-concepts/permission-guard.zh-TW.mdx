title: 權限守護
description: 基於風險的執行控制，核准可跨重啟保留，稽核完整可查。
---

權限守護位於模型與一切副作用之間。它依據工具上宣告的風險分類，套用策略；當答案是「詢問」時，它掛起工作，而不是猜測。

## 風險模型

四個等級，各自對應一個動作：

| 風險 | 預設動作 | 典型工具 |
|------|----------|----------|
| `low` | `auto` | 讀取、查詢、發現、程式碼骨架 |
| `medium` | `notify` | 建立/更新任務、新增文章、儲存回顧 |
| `high` | `confirm` | 刪除、派發 Agent、執行任務圖 |
| `critical` | `deny` | 除非有顯式授權，否則拒絕 |

按應用的覆寫可以收緊或放寬某一級（在構造守護時傳入，目前守護行程使用預設策略）：

```ts
appPermissions: {
  "some-app": { write: false, execute: false }
}
// medium → confirm（write: false）
// high   → deny   （write: false）
// critical → deny （execute: false）
```

語音執行更嚴格：只有唯讀動作自動放行，其餘都需要確認。

## 為什麼風險必須宣告

從工具名與參數推斷風險會朝一個可預測的方向失敗。`dispatch_agent`、`run_task_graph` 不含任何危險詞，卻會派生寫入檔案、執行指令的執行；名稱推斷把它們判為 `low`，而預設策略會放行。因此註冊中心要求每個原生工具顯式宣告風險。

## 核准流程

```text
工具呼叫或執行器權限請求
  → 從工具定義讀取風險
  → 策略：auto / notify / confirm / deny
  → confirm：持久化核准請求
      - 動作摘要（究竟會執行什麼）
      - 風險、範圍、過期時間
  → 掛起執行
  → 介面決定：核准 / 拒絕 / 記住
  → 恢復服務繼續或終止執行
  → 無論結果如何都寫稽核
```

由於核准被持久化，守護行程重啟不會遺失待決定請求。`POST /api/approvals/expire-stale` 關閉無人應答的請求；無人值守期累積的佇列可用批次端點處理。

## 權限記憶

「記住」會把決定記錄在動作摘要上，因此同一動作不會再被詢問。作用域是摘要級的：不同路徑、指令或參數集合對應不同摘要，會再次詢問。

## 稽核

每次決定都會寫入操作者、動作、風險、決定與結果。可透過 `GET /api/audit` 按 `actor`、`action`、`riskLevel`、`since`、`limit`、`offset` 查詢。

稽核日誌與事件日誌是分開的：稽核回答「什麼被允許或拒絕了」，事件回答「這次執行中發生了什麼」（`GET /api/events`）。

## 查看狀態

- `GET /api/approvals` — 待定與最近的核准
- `GET /api/approvals/:id` — 單一請求
- `POST /api/approvals/:id/approve` / `deny` / `remember`
- `GET /api/audit?riskLevel=high` — 高風險決定
