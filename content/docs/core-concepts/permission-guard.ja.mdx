---
title: パーミッションガード
description: リスクベースの実行制御。承認は再起動をまたいで残り、監査は完全に追える。
---

パーミッションガードはモデルとあらゆる副作用の間に立ちます。ツールに宣言されたリスクで分類し、ポリシーを適用し、答えが「尋ねる」なら作業を止めます。推測はしません。

## リスクモデル

4 段階で、それぞれがアクションに対応します：

| リスク | 既定アクション | 代表的なツール |
|--------|----------------|----------------|
| `low` | `auto` | 読み取り、照会、発見、コードスケルトン |
| `medium` | `notify` | タスク作成/更新、記事追加、振り返り保存 |
| `high` | `confirm` | 削除、エージェント委譲、タスクグラフ実行 |
| `critical` | `deny` | 明示的な付与がない限り拒否 |

アプリ単位の上書きで 1 段階だけ締めたり緩めたりできます（ガード構築時に渡す。現在のデーモンは既定を使用）：

```ts
appPermissions: {
  "some-app": { write: false, execute: false }
}
// medium → confirm（write: false）
// high   → deny   （write: false）
// critical → deny （execute: false）
```

音声実行はより厳格です：読み取り専用のみ自動承認、それ以外は確認が必要。

## なぜリスクを宣言するのか

名前や引数からの推測は予測可能な方向に失敗します。`dispatch_agent`、`run_task_graph` は危険語を含みませんが、ファイルを書きコマンドを実行する実行を派生します。名前推測では `low` となり、既定ポリシーが通してしまいます。だからレジストリはすべてのネイティブツールに明示的なリスクを要求します。

## 承認フロー

```text
ツール呼び出し / エグゼキューターの権限要求
  → ツール定義からリスクを読む
  → ポリシー：auto / notify / confirm / deny
  → confirm：承認リクエストを永続化
      - アクションダイジェスト（何が実行されるか）
      - リスク、範囲、期限
  → 実行を停止
  → UI の決定：承認 / 拒否 / 記憶
  → 再開サービスが続行または失敗させる
  → いずれの場合も監査を書き込む
```

承認は永続化されるため、デーモン再起動で保留中の決定は失われません。`POST /api/approvals/expire-stale` は誰も答えなかったリクエストを閉じ、無人運用で溜まったキューはバッチエンドポイントで処理できます。

## 権限メモリ

「記憶」はアクションダイジェストに対して決定を記録するため、同じアクションを二度尋ねません。スコープはダイジェスト単位です。異なるパス・コマンド・パラメータ集合は別のダイジェストになり、再度尋ねます。

## 監査

決定ごとに実行者、アクション、リスク、決定、結果が書き込まれます。`GET /api/audit` で `actor`、`action`、`riskLevel`、`since`、`limit`、`offset` により照会できます。

監査ログとイベントログは別物です：監査は「何が許可/拒否されたか」、イベントは「この実行中に何が起きたか」（`GET /api/events`）に答えます。

## 状態を調べる

- `GET /api/approvals` — 保留中と最近の承認
- `GET /api/approvals/:id` — 単一リクエスト
- `POST /api/approvals/:id/approve` / `deny` / `remember`
- `GET /api/audit?riskLevel=high` — 高リスクの決定
