---
title: 权限守卫
description: 基于风险的执行控制，审批可跨重启保留，审计完整可查。
---

权限守卫位于模型与一切副作用之间。它依据工具上声明的风险分类，套用策略；当答案是“询问”时，它挂起工作，而不是猜测。

## 风险模型

四个等级，各自映射到一个动作：

| 风险 | 默认动作 | 典型工具 |
|------|----------|----------|
| `low` | `auto` | 读取、查询、发现、代码骨架 |
| `medium` | `notify` | 创建/更新任务、添加文章、保存回顾 |
| `high` | `confirm` | 删除、派发 Agent、执行任务图 |
| `critical` | `deny` | 除非有显式授权，否则拒绝 |

按应用的覆盖可以收紧或放宽某一级（在构造守卫时传入，当前守护进程使用默认策略）：

```ts
appPermissions: {
  "some-app": { write: false, execute: false }
}
// medium → confirm（write: false）
// high   → deny   （write: false）
// critical → deny （execute: false）
```

语音执行更严格：只有只读动作自动放行，其余都需要确认。

## 为什么风险必须声明

从工具名与参数推断风险会朝一个可预测的方向失败。`dispatch_agent`、`run_task_graph` 不含任何危险词，却会派生写入文件、执行命令的运行；名称推断把它们判为 `low`，而默认策略会放行。因此注册中心要求每个原生工具显式声明风险。

## 审批流程

```text
工具调用或执行器权限请求
  → 从工具定义读取风险
  → 策略：auto / notify / confirm / deny
  → confirm：持久化审批请求
      - 动作摘要（究竟会执行什么）
      - 风险、范围、过期时间
  → 挂起运行
  → 界面决定：批准 / 拒绝 / 记住
  → 恢复服务继续或终止运行
  → 无论结果如何都写审计
```

由于审批被持久化，守护进程重启不会丢失待决定请求。`POST /api/approvals/expire-stale` 关闭无人应答的请求；无人值守期累积的队列可用批量端点处理。

## 权限记忆

“记住”会把决定记录在动作摘要上，因此同一动作不会再被询问。作用域是摘要级的：不同路径、命令或参数集合对应不同摘要，会再次询问。

## 审计

每次决定都会写入操作者、动作、风险、决定与结果。可通过 `GET /api/audit` 按 `actor`、`action`、`riskLevel`、`since`、`limit`、`offset` 查询。

审计日志与事件日志是分开的：审计回答“什么被允许或拒绝了”，事件回答“这次运行中发生了什么”（`GET /api/events`）。

## 查看状态

- `GET /api/approvals` — 待定与最近的审批
- `GET /api/approvals/:id` — 单个请求
- `POST /api/approvals/:id/approve` / `deny` / `remember`
- `GET /api/audit?riskLevel=high` — 高风险决定
