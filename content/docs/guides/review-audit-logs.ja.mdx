CoreLayer のすべてのツール実行決定は記録されます。本ガイドでは監査エントリの照会と読み方を説明します。

## 監査ログへのアクセス

監査エントリは `GET /api/audit` で提供され、コントロールセンターにも表示されます。承認（`/api/approvals`）やイベントログ（`/api/events`）とは別のリソースです。

## ログエントリの形式

エントリには次が記録されます：

```text
createdAt          2026-10-21T14:32:01Z
actor              jarvis
action             tool.execute
resource           filesystem:write /workspace/README.md
riskLevel          high
permissionDecision confirm
confirmedByUser    true
result             success
metadata           { ... }
```

## ログの絞り込み

`GET /api/audit` は次を受け付けます：

- `actor` — 実行者
- `action` — 実行された内容
- `riskLevel` — `low` | `medium` | `high` | `critical`
- `since` — ISO タイムスタンプの下限
- `limit` / `offset` — ページング

レスポンスは `{ entries, total, count }`。

## 一般的な用途

### セキュリティレビュー

どの高リスク操作が承認されたかを確認：

1. `GET /api/audit?riskLevel=high&since=2026-10-01T00:00:00Z` を照会
2. 各エントリの `resource` と `metadata` を確認
3. 手動決定を想定した箇所で `confirmedByUser` が `true` か確認

### デバッグ

ツール呼び出しが実行されなかった理由を探す：

1. `action` で絞り込む
2. `permissionDecision` を確認 — `deny` はポリシーによるブロック
3. `GET /api/runs/:id/events` で run id を突き合わせる

### コンプライアンス

状態変更操作の記録を作る：

1. `riskLevel=high` で照会し、続けて `riskLevel=critical` で照会
2. 返されたエントリをエクスポート
3. `confirmedByUser: false` のエントリをすべて確認 — それらは自動決定

## ログの保持

保持期間の設定はありません。エントリは設定されたデータベースの `audit_log` テーブルに残り続けます。本ページの過去版は `permissions.auditRetentionDays` を説明していましたが、そのオプションは存在しません。増加を抑えたい場合は SQL やデータベースのツールで削除してください。
